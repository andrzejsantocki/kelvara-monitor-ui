Position security for Solana DeFi

Protect the position,
not just the wallet.

Kelvara is a self-custodial position-security and incident-response layer for professional onchain allocators. It connects capital to the controls, safeguards, evidence, and response paths that matter to each exact position.

Self-custodialYour wallet remains the authority. Kelvara does not receive arbitrary control over your assets.
Position-specificEvery finding is evaluated against the exact vault and capital it can affect.
Evidence-backedIf current evidence cannot verify a condition, Kelvara does not call it safe.
How to read capability labels. Live means observable in the current Mainnet service. Beta means the production path exists but coverage or availability remains constrained. Devnet means demonstrated only in the test environment. Planned describes product direction—not current functionality.

Product documentation

Overview

A position is Kelvara's root product object. The product follows a simple chain:

01What capital is in the position?
02What controls it, and what state is expected?
03What is true now, and what changed?
04How serious is the change?
05What evidence supports the conclusion?
06What can the owner do?

The workspace mirrors this model: Overview, Positions, Governance, Safeguards, Protection, Account.

Overview answers four questions

  • Which eligible positions were recognized?
  • Does any position need attention?
  • Is current evidence available?
  • Is a response prepared for an eligible position?

Positions

Kelvara starts from the vault position—not from a generic protocol status. A position can link value, protocol, vault, deposit asset, program, governance, safeguards, and protection readiness.

Position isolation

Evidence and safeguard results remain scoped to a stable position target. A problem in one vault must not make an unrelated position appear unhealthy.

Discovery and eligibility

The public supported-position registry currently returns two Mainnet Kamino kVault subjects. Wallet inspection determines whether the connected owner actually holds an eligible position. Registry support, active monitoring, and protection eligibility are separate capabilities.

Governance

Governance answers: who controls this position right now? It is a first-class read-only product area, separate from general safeguards.

Control Map

For mapped positions, Kelvara can represent the governance provider, controlling multisig, vault identity, membership, threshold, permissions, current actions, and finalized history. The customer contract remains provider-neutral; Squads V4 is the current adapter.

Actions and history

  • Requires attention: active actions whose decoded intent or lifecycle needs review.
  • Current actions: proposals still moving through approval, rejection, threshold, timelock, cancellation, or execution states.
  • Recent changes: finalized terminal activity retained as history.

Unknown or partially decoded instructions remain explicit. Kelvara does not invent intent from an unresolved instruction.

Safeguards

Safeguards continuously compare an expected position state with current verified evidence.

Safeguard groups

  • Governance and admin controls
  • Program upgrades
  • Withdrawal and vault access
  • Oracle and asset integrity
  • Economic and configuration limits
  • Evidence integrity
Coverage varies by integration. These groups define the product model. The interface must show actual rule coverage per position; an absent or unprovisioned rule is not an implied pass.

State and severity

Customer-facing states distinguish intact, informational change, warning, critical action window, critical act-now, and unknown. Unknown, stale, unavailable, and not monitored are never rendered as safe.

Historical truth

Governance responses expose recent finalized activity, with pagination scoped to the matching wallet and vault. When a governance refresh fails, the current UI can preserve the last valid result while marking freshness stale. Append-only safeguard transitions, daily worst state, and a 90-day safeguard history remain planned; they are not claimed as current production behavior.

Protection

Protection is the owner-controlled response layer. Monitoring identifies change; protection prepares an exact action before an incident.

Kelvara ExitRail

Sign once. Keep your exact exit ready.

An ExitRail authorization consists of wallet-signed evacuation transactions whose signed message fixes the destination, accounts, instructions, and amounts. Altering that message invalidates the signature. Durable nonce accounts can keep the exact authorization usable beyond the recent-blockhash window until the nonce is consumed or deliberately advanced.

Kelvara execution

Kelvara may submit only an exact transaction already authorized by the owner and only after the configured policy and evidence checks permit submission.

Local execution

The intended integration model supplies position-specific incident evidence and response context to owner-operated infrastructure. Public production availability of this developer path is not yet documented as live.

Current production boundary

Beta Mainnet. The current app exposes immediate owner-approved evacuation and protection enrollment for the Steakhouse USDG position. The existing public production evidence does not establish autonomous Mainnet detection-to-broadcast as generally available. The end-to-end autonomous incident journey remains a Devnet proof.

Removal and revocation

Unused authorization can be invalidated by advancing or reclaiming its nonce accounts. The app distinguishes active resources from resources that are releasable after protection removal.

Evidence & monitoring health

Evidence is part of the product contract—not an implementation footnote. A conclusion can carry the network, exact subject, vault or multisig, finalized slot, observation time, hashes, decoder provenance, source, and evidence reference.

Current versus last verified

Current answers what Kelvara can verify now. Last verified records the most recent successful observation. A previous good result cannot remain a current green state after fresh evidence disappears.

Monitoring health

HealthyCurrent evidence is available within its freshness policy.
StaleEvidence exists but is too old to support a current-safe conclusion.
UnavailableThe expected observation path failed or returned unusable evidence.
Not monitoredNo active observation capability is configured for this subject.

Kelvara therefore monitors both the position and its ability to keep observing the position.

Account, wallet & network

The connected wallet establishes identity; it does not transfer custody. Sessions are bound to the selected network and genesis identity. Switching networks clears incompatible session and cached state.

  • Mainnet and Devnet remain isolated contexts.
  • Authentication uses a wallet-signed challenge and short-lived session.
  • Account surfaces show access, coverage period, wallet connection, and security controls.
  • Read-only governance and position data remain distinct from signing actions.

Security model

  • No key custody. Kelvara does not receive seed phrases or private keys.
  • No general wallet authority. Wallet connection or message authentication does not grant arbitrary transaction rights.
  • Bounded authorization. Prepared transactions are constrained to the reviewed position, owner destination, instruction sequence, signer set, and fee policy.
  • Independent validation. Transactions are decoded, simulated, and checked before and after owner signature.
  • Encrypted authorization storage. Stored signed authorization is encrypted where protection enrollment applies.
  • Fail closed. Missing, malformed, stale, or mismatched evidence is not a pass.
  • Replay and uncertainty handling. Nonce state and submitted signatures prevent blind retries when submission outcome is uncertain.

Program upgrades

A stable program address does not imply stable code. A transaction validated under earlier program semantics must not automatically remain trusted after arbitrary bytecode change. Code changes require quarantine and renewed validation.

Limitations

  • Kelvara cannot predict every exploit or protocol failure.
  • Monitoring does not guarantee enough time or liquidity to exit.
  • Authority continuity alone does not prove code, dependencies, governance, or economic assumptions safe.
  • Evacuation still depends on the protocol and Solana accepting the exact withdrawal.
  • Coverage differs by position. Unsupported or unprovisioned checks remain explicit.
  • Kelvara is not insurance, an audit, investment advice, or a guarantee against loss.

Developer documentation

Developer overview

Developer contracts use canonical identifiers and preserve network, subject, version, provenance, and uncertainty. Public read-only routes and authenticated owner routes have different trust boundaries.

GET/healthz

Public service health. Component health fields must be interpreted separately; an HTTP 200 is not proof every monitor is active.

GET/api/supported-positions?network=mainnet-beta

Public canonical catalog for discoverable position subjects and per-subject capability state.

GET/api/config

Legacy active evacuation-integration configuration. Do not use as the complete supported-position registry.

Wallet portfolio, governance, account, evacuation, and protection routes require network-bound authentication where owner context or action authority is involved.

ExitRail API

ExitRail is the developer-facing protection concept. The current production UI uses legacy evacuation and protection route names; the stable public ExitRail API naming and broad integration contract should be treated as planned until separately released.

Lifecycle contract

  1. Prepare: construct an exact position exit and return reviewable metadata.
  2. Authorize: owner wallet signs the exact transaction set.
  3. Status: report readiness, variants, nonce state, and removal requirements without returning secret bytes.
  4. Incident input: bind current position evidence to a versioned policy.
  5. Execute: validate immutable identity, simulate, atomically claim, submit once, and reconcile finality.
  6. Revoke: remove unused authorization by advancing or reclaiming nonce resources.
Release boundary. This lifecycle describes the security contract. It does not claim a generally available autonomous Mainnet endpoint.

Evidence, governance & safeguard contracts

Canonical position identifier

solana:{network}:{protocol}:{resourceType}:{address}

Governance

Governance payloads separate provider identity, membership, attention-required actions, current actions, terminal history, freshness, and pagination. Finalized history must never be inferred from only the current multisig account.

Safeguards

Safeguard records bind target ID, binding ID, rule ID and version, result, reason, and evidence reference. Projection must retain target scoping and cannot relabel unknown private evidence as verified.

Evidence

Evidence receipts preserve source and observation identity. Current evaluation and last successful verification are separate fields and separate customer claims.

Webhooks & local executor

The local-executor model is owner-operated: Kelvara supplies incident signal, exact subject, policy identity, evidence reference, and prepared-response context; owner infrastructure decides whether to submit. Authentication, replay protection, idempotency, and uncertain-send reconciliation are required. Public production availability is planned, not claimed here.

Errors & fail-closed semantics

  • Wrong network or genesis identity: reject and clear incompatible state.
  • Unknown subject or unsupported position: return explicit unsupported state.
  • Stale or unavailable evidence: return unknown/unavailable, never pass.
  • Malformed governance instruction: preserve raw provenance and unresolved status.
  • Simulation failure: signing or submission remains blocked.
  • Submission timeout: preserve pending state and reconcile the known signature; do not blindly retry.
  • Immutable transaction mismatch: reject before broadcast.
